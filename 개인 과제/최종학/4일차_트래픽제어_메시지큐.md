# 4일차: 대용량 트래픽 제어와 메시지 큐 (Asynchronous & Throttling)

## 1. 개요
Riot API의 Rate Limit(20초당 100회, 2분당 100회 등)과 대용량 전적 데이터(유저당 2,000판) 수집 간의 충돌 문제를 해결하기 위해, **메시지 큐(Message Queue)**를 도입하고 **생산자-소비자(Producer-Consumer) 패턴**을 적용함.

## 2. 문제 상황 분석 (Why Message Queue?)

### A. 동기 처리(Synchronous)의 한계
* **시나리오:** 회원가입 시 2,000판의 전적을 모두 조회하려고 시도.
* **계산:** * Match ID 목록 조회: 1회 (100개씩 끊어도 20회)
    * Match 상세 조회(Bottleneck): 2,000회 요청 필요.
    * Riot 제한: 100 requests / 2 min (Development Key 기준).
* **결과:** 1.  **UX 박살:** 사용자는 회원가입 완료까지 최소 40분 대기해야 함.
    2.  **429 Error:** 라이엇 서버로부터 "Too Many Requests" 차단 당함.
    3.  **Thread Blocking:** 톰캣 스레드가 API 응답 기다리느라 고갈됨.

### B. 해결 아키텍처 설계 (Event-Driven)
* **전략:** "일단 가입 시켜주고, 전적은 나중에 몰래 가져오자."
* **Flow:**
    1.  **Web Server:** 최근 20게임만 조회 후 즉시 응답 (User Experience 확보).
    2.  **Producer:** "이 유저의 나머지 전적 갱신해!"라는 메시지(Event)를 큐(Queue)에 발행(Publish).
    3.  **Queue:** 메시지를 쌓아둠 (RabbitMQ, Redis List, Kafka 등).
    4.  **Consumer (Worker):** 별도의 스레드가 큐에서 메시지를 하나씩 꺼내 API 요청 수행.

## 3. 핵심 기술 요소 (Deep Dive)

### A. Message Queue 선택 (RabbitMQ vs Redis)
* **Redis (List/PubSub):** 이미 캐시용으로 쓰고 있다면 도입이 쉬움. 가볍고 빠름. (이번 프로젝트에 적합)
* **RabbitMQ:** 메시지 영속성(서버 꺼져도 데이터 보존), 라우팅 등 엔터프라이즈 기능 강력함.
* **선택:** (본인이 선택한 기술 적기, 예: 인프라 복잡도를 낮추기 위해 Redis 사용)

### B. Rate Limiting (속도 제어) - "Leaky Bucket 알고리즘"
* **개념:** 큐에 작업이 10,000개가 쌓여 있어도, Consumer가 수도꼭지(Bucket)를 조절해서 1초에 5개씩만 API를 호출하게 만듦.
* **구현 도구:**
    * **Bucket4j (Java Library):** 로컬 혹은 분산 환경에서 토큰 버킷 알고리즘 지원.
    * **Resilience4j:** RateLimiter 모듈 제공.
* **적용:** 라이엇 API 키 등급에 맞춰 `1초당 허용 요청 수`를 설정하고, 이를 초과하면 Consumer가 잠시 `sleep` 하도록 구현.

## 4. 구현 및 실습 (Implementation)

### A. Producer (Controller 단)
```java
// 최근 20게임은 바로 리턴
matchService.fetchRecentMatches(puuid);

// 나머지는 큐에 던짐 (비동기)
rabbitTemplate.convertAndSend("match.queue", new MatchSyncMessage(puuid));

```

### B. Consumer (Worker 단)

```java
@RabbitListener(queues = "match.queue")
public void syncAllMatches(MatchSyncMessage message) {
    // 1. Rate Limiter 체크 (토큰 없으면 대기)
    if (rateLimiter.tryAcquire()) {
        // 2. 라이엇 API 호출 (상세 전적)
        matchService.fetchAll(message.getPuuid());
    } else {
        // 토큰 찰 때까지 대기 or 다시 큐에 넣기
    }
}

```

## 5. 결론

* **UX 개선:** 사용자는 대기 시간 없이 서비스를 이용함.
* **안정성:** 트래픽이 폭주해도 큐(Queue)에만 쌓일 뿐, API 서버는 일정한 속도로 처리하므로(Rate Limiting) 429 에러나 서버 다운을 방지함.
* **확장성:** 전적 갱신 속도가 느리면 Consumer(Worker) 서버만 늘려서 해결 가능.
