실시간 경매 / 드래프트 시스템 설계 요약
1. 전체 설계 결론

이번 대화를 통해 정리된 핵심 결론은 다음과 같습니다.

실시간 경매 시스템에서는 실시간 처리 경로와 정합성 처리 경로를 분리하는 것이 가장 중요합니다.
입찰 과정에서의 판단은 Redis가 담당하고, 경매가 종료된 시점에만 RDB에 최종 결과를 저장하는 구조가 가장 안정적입니다.
MongoDB는 선택적으로 사용할 수 있는 보조 저장소이며, 핵심 판단 로직을 맡기지 않는 것이 원칙입니다.

2. 저장소별 역할 정리
   Redis의 역할

Redis는 단순한 캐시가 아니라 실시간 경매의 중심 저장소로 사용합니다.

입찰 유효성 판단

최고 입찰가 관리

동시성 제어

종료 시점 판단

최종 결과 확정 상태 보관

실시간 입찰 과정에서 발생하는 모든 경쟁 로직은 Redis 안에서 처리되도록 설계합니다.

RDB의 역할

RDB는 경매당 단 한 번만 접근하는 것을 원칙으로 합니다.

경매 종료 시 최종 결과 저장

정합성이 반드시 보장되어야 하는 데이터 관리

실시간 입찰 중에는 RDB를 사용하지 않으며, 이를 통해 트랜잭션 충돌이나 락 대기 문제를 원천적으로 피할 수 있습니다.

MongoDB의 역할

MongoDB는 필수 구성 요소는 아닙니다.

사용한다면 다음과 같은 용도로 제한하는 것이 적절합니다.

진행 상태 스냅샷 저장

UI 복구용 데이터

입찰 로그 및 감사 로그

관리자 모니터링용 데이터

MongoDB의 데이터가 유실되더라도 RDB에 최종 결과를 저장하는 데 문제가 없어야 합니다.

3. Redis 장애 대비에 대한 설계 원칙

Redis 장애를 대비해 입찰마다 MongoDB에 복구용 데이터를 저장하는 방식은 권장되지 않습니다.

이 방식은 실시간 입찰 경로를 느리게 만들고,
MongoDB를 새로운 병목 지점으로 만들어 전체 시스템 안정성을 떨어뜨릴 수 있습니다.

대신 다음과 같은 원칙을 따르는 것이 좋습니다.

Redis에 최종 결과를 확정 상태로 반드시 남긴다

Redis의 AOF와 RDB 스냅샷을 활성화한다

MongoDB는 스냅샷 또는 비동기 로그 용도로만 사용한다

복구를 위해 모든 입찰 이벤트를 저장할 필요는 없으며,
최종 상태를 재구성할 수 있는 최소한의 정보만 유지하면 충분합니다.

4. 경매 종료 처리 흐름

경매 종료 시 처리 흐름은 단순하게 유지하는 것이 가장 안전합니다.

Redis에서 경매 종료 여부 판단

Redis에 최종 결과 확정 상태 기록

RDB에 트랜잭션 1회 수행

결과 브로드캐스트

Redis 데이터 정리

이 흐름에서 MongoDB는 필수 요소가 아닙니다.

5. 일시정지(Pause) 기능 유무에 따른 설계 차이
   Pause 기능이 있는 경우

상태 머신이 필요함 (BIDDING, PAUSED, FINISHED)

남은 시간을 직접 관리해야 함

Redis TTL을 종료 기준으로 사용하기 어려움

상태와 시간 정보를 원자적으로 처리해야 함

이 경우 설계 복잡도가 크게 증가합니다.

Pause 기능이 없는 경우

상태를 BIDDING, FINISHED로 단순화 가능

종료 시각(endAt) 기반 설계

Redis TTL을 종료 트리거로 활용 가능

전체 구조가 훨씬 단순해지고 구현 부담이 줄어듦

Pause 기능이 없다면 TTL 기반 설계가 가장 자연스럽고 안정적인 선택입니다.

6. 참여자 수가 적은 경우에도 설계는 동일

경매 참여자가 10명 이내인 소규모 환경이라 하더라도 설계 원칙은 변하지 않습니다.

동시성 문제는 참여자 수가 아니라 경쟁 구조 자체에서 발생하기 때문입니다.
다만 소규모 환경에서는 Redis Cluster나 복잡한 이벤트 파이프라인 같은 고급 구성은 생략할 수 있습니다.
