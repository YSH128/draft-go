객체 지향 프로그래밍(OOP) 정리

객체 지향 프로그래밍(Object-Oriented Programming)은
프로그램을 객체(Object) 단위로 설계하고
객체 간의 책임과 협력으로 문제를 해결하는 프로그래밍 패러다임이다.

1. 객체(Object)란?

객체는 상태(State)와 행동(Behavior)을 함께 가지는 독립적인 단위이다.

상태: 객체가 가지는 데이터(필드)

행동: 객체가 수행하는 기능(메서드)

객체는 단순한 데이터 묶음이 아니라
자신의 상태를 스스로 관리하고 판단하는 주체이다.

2. 클래스와 객체의 차이

클래스(Class): 객체를 생성하기 위한 설계도

객체(Object): 클래스를 기반으로 생성된 실제 인스턴스

3. 객체 지향의 4대 특징
   3.1 캡슐화(Encapsulation)

객체의 내부 구현과 상태를 외부에 숨기고
필요한 기능만 메서드로 제공하는 개념이다.

데이터 무결성 보장

변경에 강한 구조

3.2 상속(Inheritance)

기존 클래스의 기능을 물려받아 새로운 클래스를 생성하는 방식이다.

장점: 코드 재사용성 증가

단점: 과도하면 결합도 증가

실무에서는 상속보다 조합을 선호하는 경우가 많다.

3.3 다형성(Polymorphism)

같은 메서드 호출이 객체의 실제 타입에 따라 다르게 동작하는 성질이다.

Animal animal = new Dog();
animal.eat();

3.4 추상화(Abstraction)

공통된 핵심 개념만 추출해 표현하는 것이다.

interface Payment {
void pay();
}

4. 객체 지향의 핵심: 객체의 책임

객체는

자신의 상태와 관련된 로직을 내부에 두고

스스로 판단하고 행동해야 한다.

👉 객체는 데이터 보관소가 아니라 책임을 가진 주체다.

5. TDA 원칙 (Tell, Don’t Ask)
   5.1 TDA란?

객체의 상태를 물어보고 판단하지 말고
객체에게 해야 할 행동을 직접 요청하라는 설계 원칙이다.

5.2 TDA 위반 예시
if (account.getBalance() >= amount) {
account.withdraw(amount);
}


문제점

외부에서 객체 상태 조회

판단 로직이 객체 밖에 존재

결합도 증가

5.3 TDA 적용 예시
account.withdraw(amount);

class Account {
private int balance;

    public void withdraw(int amount) {
        if (balance < amount) {
            throw new IllegalStateException();
        }
        balance -= amount;
    }
}


효과

객체 책임 명확

캡슐화 강화

변경에 강한 구조

6. 디미터의 법칙(Law of Demeter)

객체는 직접 알고 있는 객체와만 대화해야 한다는 원칙이다.

// 나쁜 예
order.getCustomer().getWallet().getMoney();

// 좋은 예
order.pay();


TDA는 디미터의 법칙을 실천하는 대표적인 방법이다.

7. 객체 지향 vs 절차 지향
   구분	절차 지향	객체 지향
   중심	함수	객체
   관점	흐름 중심	책임 중심
   변경	취약	강함
   규모	소규모	대규모
8. 실무에서 자주 깨지는 객체 지향

엔티티에 getter만 있고 로직은 서비스에 집중

if + getter 조합 남발

DTO를 도메인처럼 사용

👉 객체가 판단하지 않고 외부에서 판단하는 구조

9. 좋은 객체 지향 코드의 특징

객체가 스스로 판단한다

getter 사용이 최소화된다

책임이 명확하다

변경 시 영향 범위가 작다

10. 한 줄 요약

객체 지향 프로그래밍은
객체에 책임을 부여하고 객체 간 협력을 통해
변경에 강한 구조를 만드는 설계 철학이다.
